# Keeta App 数据采集可行性分析

日期：2026-10-23（第二版，结合仓库现状更新）
目标：采集 Keeta App（巴西，圣保罗 + 桑托斯）结算页（P3）红框内尽可能多的真实数据，用于 ETA gap 监控。

## 1. 结论摘要

- **官方 Open API 无法提供红框报价数据。** 它是商家侧接口（订单、菜单、门店），不含消费者结算页的个性化报价与 ETA。但经商家授权后，门店主数据接口可补 `shop_id`、`shop_lat`、`shop_lng`（理论上 22 项可到 25 项，未实测）。
- **消费者端私有接口没有公开文档。** 端点、鉴权和签名机制无法确认。逆向签名、绕过风控、伪装设备或定位不在建议范围内。
- **数据采集本身可做，但目前只有单条 PoC 加连续采集试运行。** 仓库已有 v4 单条管线和 stream 连续管线，约 22/30 字段，8 条真实记录后出现 `Access error`，采集保持暂停。没有生产吞吐量证据，每周 3 万条目前无法承诺。
- **被锁的原因尚未确定。** 只有一个 `Access error` 页面，没有 HTTP 状态码、验证码或限制原因，无法判断触发维度、阈值或恢复时间。
- **想要稳定和合规，最终要靠商务授权或购买数据。** 巴西用户条款 §4.1.6 明确限制未经书面许可的自动抓取。

## 2. 官方 API 调研

入口：`open.mykeeta.com/api/open`，文档站 `api-docs.mykeeta.com`；巴西官网有 API 集成入口，指向 `developers.mykeeta.com`。

### 体系
- Open Delivery API（基于 Open Delivery 规范）
- Standard Keeta API（Order / Menu / Product / Store）
- Grocery Keeta API

### 准入流程
1. 开发者站注册，约 5 个工作日审核
2. 签 NDA，获得开发者账号和测试门店
3. 开发并做 SIT 联调
4. 品牌注册
5. 每个品牌强制 UAT（需配合一家真实餐厅）
6. SIT 通过后分配生产环境 AppId 和 Secret

### 数据边界
- 调用需要门店 token，来自商家在 Keeta 商家后台的授权
- 只能读写已授权门店自己的菜单、商品、订单
- 限流按 appId 计 QPS，菜单类接口约 10–100 QPS。**这是商家集成接口的配额，不能当作消费者 App 的允许访问频率。**

### 对字段的覆盖
| 字段类别 | 官方 API |
|---|---|
| 门店 ID、名称、地址、经纬度（已授权门店） | 可补 `shop_id`、`shop_lat`、`shop_lng`；需商家授权 |
| 菜单、SKU、规格（已授权门店） | 可用于构建固定篮子；商家菜单价不等于消费者券后价 |
| ETA 区间、配送费、服务费、券后价 | 无 |
| 未授权门店的任何数据 | 无 |
| `account_id` | 无。文档中的 `userId` 是品牌账号，不是消费者账号 |

## 3. 路径对比

| 路径 | 能否拿到红框数据 | 风险 / 说明 |
|---|---|---|
| 官方 Open API | 否（仅补门店主数据） | 仅商家侧，需授权 |
| 私有接口重放 | 技术上可能，未验证 | 签名、证书固定、风控；违反条款，不建议 |
| App 端采集（降量、带熔断） | 是 | 现有路径，字段约 22/30；仍有访问限制风险 |
| 数据供应商 | 需实样验收 | NenoData、Food Data Scrape 等自述可评估巴西，未取得实样与授权证明，不能视为已验证 |
| Keeta 商务合作 | 是（需谈判） | 最稳定，周期和结果不确定 |
| 用户自愿面板 | 是（覆盖有限） | 合规性最高 |

## 4. 风控：现有证据与三条假设

### 4.1 现场证据
- 会话约 28 分钟，保存 8 条记录（各 22/30），期间 20 个尝试目录、19 次店铺详情采集（13 家不同店）、9 次结算顶部采集。
- 这些是本地页面读取次数，**不是 HTTP 请求数**；真实请求数和缓存命中情况未知。
- 错误是 App 页面 `Access error / Please try again later`，不是已确认的 429，也不是锁屏。
- 设备时区实测为 `America/Sao_Paulo`；Android 全局代理为空，但这**不能证明**出口 IP 地区。
- `keeta_stream.py` 默认间隔 `--interval 30`。

### 4.2 三条常被提到的假设（均未验证）
1. IP 国家、收货地址、GPS 三者不一致。注意：出口 IP 地区从未验证，该组合现在是否存在本身不确定。
2. 0 单账号反复进入结算页且从不下单。与日志吻合，但不能据此证明。
3. 操作节奏固定、过于整齐。stream 默认固定间隔，吻合，同样不能证明。

"权重很高""结算页权重最高"属于 Keeta 内部风控模型，外部无法得知，不应写成事实。单次 `Access error` 无法区分这三条。

### 4.3 不采纳的做法
这三条假设描述的是一个未下单、持续探测结算页、节奏固定的自动化流量。顺着它们去"整改"，本质是让自动化看起来像真人，包括：

- 伪造定位、更换或购买巴西住宅 IP
- 为间隔加随机抖动以模拟人工节奏
- 养号以掩盖 0 单画像、批量注册账号或扩大账号池分摊配额
- 被锁后换账号、网络或设备硬顶

这些做法不采纳。理由：规避平台检测、违反条款 §4.1.6、提高永久封禁和账号连坐风险。仓库 `CLAUDE.md` 的操作边界（限流时暂停，不换 IP/账号/设备绕过）与此一致。

仓库中 `docs/ac-br-API与风控评估.md` 的 §3.4（养号、固定住宅 IP）和 §4（100–190 个账号/设备池）属于上述范围，本文不采纳，建议另行修订。

### 4.4 对"配额标定"的更正
上一版和 TODO 中的 C8（单账号按 20/40/80/120 条/天逐档跑到被锁来找上限）是主动试探限制，等于刻意触发风控，本文**不建议**。配额应由 Keeta 书面告知，而不是靠撞锁反推。

## 5. BRD 核对与优化建议

### 5.1 工作量算术
- BRD 公式 `2城 × 500 × 1次 × 1账号 × 5距离 × 2轮` 实际乘积为 **10,000**，不是 5,000（仓库 B1 同样指出）。
- 三类账号全采约 30,000 次/周，与 project.md 一致。

### 5.2 单账号负载（示例）
- 15,000 次在 12 小时内完成，需 1,250 次/小时。
- 按 6 个账号均摊约每账号每 17 秒一次结算预览。这是容量算术，说明现有设计与"低频访问"相冲突，**不是**扩大账号池的理由。

### 5.3 抽样设计
ETA gap 监控的目标是城市级聚合指标，不是全店覆盖。

- **固定面板**：约 100 家店 × 5 个距离段，用于趋势对比。
- **轮转面板**：其余店轮转，用于覆盖。
- 样本量参考（假设 ETA 标准差约 5 分钟，均值误差 ±1 分钟）：每个分层（城市 × 账号类型 × 时段）约 100 个样本。是估算，需首批数据校准。
- 预计请求量可降 3–5 倍。

### 5.4 字段口径
结算页价格受优惠券影响。建议新增并记录：`coupon_available`、`coupon_applied`、`guaranteed_time_promo`、`cart_spec`，且不自动叠加优惠。仓库 B11 已有类似要求。

### 5.5 购物车标准化
固定购物车规格（如起送价附近的单件商品），保证跨店可比。

## 6. 字段来源分层（对应仓库现状）

| 数据层 | 字段 | 来源 | 现状 |
|---|---|---|---|
| 实时条件化报价 | ceta_min/max、product_*、delivery_*、service_*、total_*、shop_name、shop_status | 结算页、店铺页 | 已能读取 |
| 自有上下文 | crawl_address、account_type、user_completed_orders_count | 地址栏、订单页 | 已能读取（需页面明确显示） |
| 店铺主数据 | shop_id、shop_lat、shop_lng、shop_address | 商家授权接口，或店铺页 | 目前缺失；授权后可补前三项 |
| 难补字段 | account_id、is_member、crawl_lat/lng、distance | 需独立核验来源 | 目前缺失，不用推测或地理编码冒充 |

## 7. 建议行动

工程侧（不涉及规避检测）：
1. **持久熔断**：首次 `Access error` 写入状态文件，进程重启仍默认暂停，需人工确认恢复。
2. **操作预算日志**：记录每次导航、页面、起止时间和结果。
3. **店铺主表缓存**：在允许的周期内复用，避免每条报价都进详情页。
4. **固定篮子与固定店铺队列**：减少规格失败和重复导航。
5. **解析失败离线重放**：证据已在本地时先修解析，不为布局变化重新访问同店。
6. 按 5.3 调整抽样设计。

业务侧：
1. 向 Keeta 技术团队提出 6 项问题（见 `docs/oc-keeta-access-and-scale-research.md`）：数据用途许可、下单前报价或 ETA 接口、可书面允许的采样方案、授权店铺范围、配额与恢复流程、测试环境。
2. 并行评估数据供应商，**先要求巴西指定城市的实样**和 30 字段逐项来源，再谈规模。
3. 上量前做法务评估（平台条款、LGPD）。

## 8. 待确认事项

- 红框数据是客户自有门店还是第三方门店（决定官方 API 能否覆盖）。
- Keeta 是否有面向第三方的只读市场数据授权或书面允许的采样方案。
- 目标时效性：周度趋势还是日内实时。
- 一条记录的业务定义：店铺 × 账号上下文 × 地址 × 固定篮子 × 时段。
- 手机真实出口 IP 地区（只做诊断记录，不作为"整改"依据）。
