# 巴西 Keeta 真实数据采集：API 与风控评估

日期：2026-10-23
目的：在不依赖（或少依赖）App 界面的前提下，稳定拿到附图红框内的字段，尽可能提高单条记录的字段覆盖度。

## 一、结论

1. **没有可直接替代 App 的公开消费者 API。** Keeta 官方 API 都是商家侧 Open Delivery，服务对象是餐厅/POS/ERP，不是做比价的数据方。
2. **App 内部接口存在，但不可直接调用。** 无公开文档，通常带请求签名、设备指纹和证书固定；只能逆向，属于高风险 spike。
3. **风控是当前最大的不稳定因素。** 账号被临时锁定、约一天后恢复，说明是软限制而非永久封禁；继续重试会延长限制。
4. **UI 自动化仍是近期唯一能稳定产出红框字段的路线。** 但必须按“低配额 + 账号固定环境 + 熔断”的方式跑，不能按满速跑。
5. **15,000 条/次的量级与安全配额存在明显冲突。** 按 1 条/5–8 分钟/账号计算，需要约 100–170 个账号及对应设备；现有 10–12 台设备的估算只在“30 秒/条且不触发风控”时成立。

## 二、API 调研

### 2.1 官方 Open Delivery API（商家侧）

入口：`api-docs.mykeeta.com/apis/opendelivery`

已确认的能力：

- 商家 OAuth 授权（merchant self-serve authorization），每个调用只代表一个已授权商家。
- 订单生命周期：确认订单、备货完成、商家履约、轮询/Webhook。
- Menu API：商家把**自己的**菜单同步给 Keeta，是写入/同步接口，不是读取接口。
- 实际接入多由 Linx、Consumer、PDV Legal、Xmenu 等 POS/ERP 厂商完成；底层遵循 Abrasel Open Delivery 规范（当前可见 1.6.0）。

限制：只能访问已授权的商家，不能按任意收货地址查询全量店铺的菜单、价格、配送费和 ETA，回答不了“某店送到某地址多少钱”。因此不能作为本项目的消费者价格数据源。

### 2.2 Menu API

`api-docs.mykeeta.com/apis/standard/docs/menuintegrationguide` 描述的是商家上传/同步菜单，用于让 Keeta 展示菜品。它不是面向消费者的查询接口，也不能跨店读取。

### 2.3 App 内部接口

App 的列表、店铺、购物车、结算数据都来自后端接口，但：

- 没有公开文档和稳定契约；
- 预计有请求签名、时间戳/nonce、设备指纹；
- Android 7+ 默认不信任用户 CA，且 App 很可能有证书固定；
- 需要 root + Frida/mitmproxy 才能尝试重放，且接口随时可能变。

这属于 `TODO.md` 的 C5 spike，不是“可以调用的 API”。即使打通，也只能降低单条耗时，不能消除账号/地址矩阵和风控。

### 2.4 对红框字段的影响

| 来源 | 能拿到的红框字段 | 备注 |
| --- | --- | --- |
| 商家 Open Delivery / Menu API | 自家店铺的菜单、订单 | 拿不到竞对/全量消费者价格与 ETA |
| App 内部接口（若逆向成功） | 列表、店铺、购物车、结算的结构化数据 | 需签名/证书/风控，维护成本高 |
| UI 自动化（现状） | 全部可见字段 | 稳定但慢，受风控限制 |

## 三、风控与限流

### 3.1 现象

- 持续采集时突然无法访问，约一天后恢复，恢复时间不确定。
- 更像账号级或设备/IP 级的临时限制，而不是永久封禁。
- 被锁后继续重试，通常会延长限制时间。

### 3.2 先定位锁的是哪一层

| 测试 | 结果 | 判断 |
| --- | --- | --- |
| 同一设备换一个账号 | 正常 | 账号级 |
| 同一账号换网络/设备 | 正常 | 设备或 IP 级 |
| 两者都失败 | 仍不可用 | 区域/网络或更上层限制 |

下次被锁时保留提示页截图，才能判断是“异常活动”“访问受限”还是内容空白/强制退出。

### 3.3 最可能的触发因素

- 账号新、未绑巴西手机号、无正常浏览/下单历史。
- 账号、IP、GPS、时区不一致：加拿大 IP + 圣保罗坐标 + 温哥华时区。
- 高频进入结算页。`加购 → Checkout` 是高风险动作，比浏览列表更容易触发。
- 单账号短时间请求量过高，或多个会话并发。
- 被锁后继续重试。

### 3.4 降低触发率的做法

1. **被锁即停。** 该账号冷却 24–48 小时，不重试、不换号硬顶。
2. **身份固定。** 一个账号固定一台设备、一个巴西住宅 IP、一个收货地址；账号、IP、GPS、时区保持一致。
3. **先养号。** 新账号先正常浏览、搜索、加购 3–7 天，最好有真实下单记录，再开始采集。
4. **控制强度。** 起步按 1 条/5–8 分钟，单账号每天 80–100 条以内；每 2 小时休息 15–20 分钟。
5. **结算页配额。** 能停在店铺页拿到的字段就不要进结算；必须取配送费/服务费时才进 Checkout，单账号每小时控制在个位数。
6. **熔断。** 出现验证码、429、内容空白、强制登录任一信号，立即暂停该账号并进入冷却。
7. **账号健康状态机。** `active / cooldown / banned` 三态，配合日配额、最小间隔、同账号串行，不做并发。

不建议：每请求换 IP、伪造设备指纹、批量注册小号。这些做法短期看似有效，实际会提高永久封禁和整批账号连坐的概率，也会放大合规风险。

### 3.5 配额标定（建议先做）

单账号按每天 20 / 40 / 80 / 120 条四档，各跑 3 天，记录第几天触发限制；找到不触发上限后，生产按上限的 60–70% 设定配额。这个结果直接决定账号池和设备数。

## 四、容量与差距

按 15,000 条 / 12 小时窗口计算：

| 单账号节奏 | 每小时 | 12 小时产能 | 所需账号/设备 |
| --- | --- | --- | --- |
| 1 条/5 分钟 | 12 | 144 | 约 105 |
| 1 条/8 分钟 | 7.5 | 90 | 约 167 |
| 1 条/3 分钟 | 20 | 240 | 约 63 |

若按每天 80 条的安全配额，15,000 条需要约 188 个账号。现有 10–12 台设备、单机 30–60 秒/条的估算，只在不受风控的前提下成立，不能作为交付排期依据。

三个可选方向：

1. **降量或拉长窗口**：把 15,000/次拆成多天或多时段，按安全配额交付。
2. **扩账号池与设备池**：按标定结果配置 60–190 台设备，成本与运维显著上升。
3. **官方合作/数据授权**：绕开消费者风控，长期最稳，但需要商务谈判。

## 五、对红框字段的采集策略

字段分布在 4–5 个页面，建议分级采集，而不是每条都打满：

| 层级 | 页面 | 主要字段 | 风险 | 策略 |
| --- | --- | --- | --- | --- |
| P0 | 结算页 | 商品原价/折后价、配送费原价/折后价、服务费、总额、送达时刻、地址 | 高 | 按配额采，单账号每小时个位数 |
| P1 | 店铺页 | 店名、菜品、价格、ETA 分钟、配送费、距离 | 中 | 每条都采，作为主数据 |
| P2 | 列表页 | 店名、评分、配送费、ETA、距离 | 中 | XML 取 bounds + OCR |
| P3 | 账号页 | 账号 ID、历史单数、账号类型、会员 | 低 | 低频补齐，按账号维度缓存 |
| P4 | 商家/地理 | shop_id、店铺地址、经纬度 | 低 | 离线补齐，地理编码 |

原则：能离线补的字段不要在线打；能用店铺页拿的不要进结算；结算页只补它独有的费用字段。

## 六、下一步

1. 做 3.5 的配额标定，拿到单账号安全上限。
2. 按标定结果重算账号池、设备池和 15,000 条的交付周期。
3. 用 uiautomator2 打通 P3 XML，补齐费用行，先落一条完整实时样例。
4. 并行做 1–2 周 API spike，验收门槛：feed 与 checkout 两个请求能稳定重放；不通过就回到设备池方案。
5. 同步评估官方合作/数据授权的可行性。
