# Keeta 访问异常与规模化数据接入调查

调查日期：2026-10-23。目标：解释当前 8 条后出现的访问异常，评估 15,000 条/次、每周两次的可持续接入路径。仅查询公开资料和本地证据，未恢复受限 App 的业务采集，未提交订单、申请账号、签约或发送外部消息。

## 结论

1. 当前观测是 App 页面 `Access error / Please try again later`，不是已确认的 HTTP 429，也不是 Android 锁屏。限流/访问控制是可能原因，网络、App 页容器与服务异常也尚未排除；没有证据可确定触发维度、阈值或恢复时间。
2. “8 条有效记录”不等于“8 次访问”。本会话有 20 个尝试目录、19 次店铺详情采集（13 个不同店名）、9 次顶部与 9 次费用页采集、7 次规格页采集、3 次订单页采集、4 次进程启动。首个详情时间 12:42:59、最后一个 13:11:06，均为圣保罗时间。期间包含调试、失败与恢复，不是稳定吞吐量测试。
3. **纠正旧结论：Keeta 有公开可读的官方开发者文档和需授权的商家 API。** 巴西官网已核验 Integração via API，点击 Comece agora 打开 `developers.mykeeta.com`。这不是允许匿名读取所有消费者数据的接口。
4. 官方接口可支持获授权商家主数据；本次未找到并核实任意消费者账号、配送地址、下单前购物车报价及 ETA 的公共查询接口。不能承诺 API 可直接替代当前全部 30 字段。
5. 应优先验证授权数据范围与实时报价来源，并改进故障诊断、请求预算和静态数据复用。当前证据不足以把买设备、换网络、扩账号或未授权接口重放作为规模化解决方案。

## 官方资料核验

### 1. API 入口和接入条件

- [巴西官网](https://www.keeta-global.com/BR/pt-BR)：页面有 API 集成版块，说明订单管理、菜单同步等合作能力。已使用真实浏览器核验入口，不只依赖搜索摘要。
- [开发者门户](https://developers.mykeeta.com/)：官方入口。未登录、注册或提交表单。
- [How to Start](https://api-docs.mykeeta.com/apis/opendelivery/how-to-start)：说明联系 Keeta、NDA、开发者账号与测试 App/店铺流程。
- [General Info](https://api-docs.mykeeta.com/apis/opendelivery/general-info)：软件服务访问商家数据前需要商家授权；存在令牌、签名和商家授权流程。菜单同步及订单接口属于商家集成，不是全市场消费者数据授权。

### 2. 可补齐的字段与边界

[Get Authorized Merchant Store List](https://api-docs.mykeeta.com/apis/opendelivery/authentication/getmerchantinfo.md) 文档明确包含：获授权门店 ID、名称、地址、经纬度和时区。若具备对应商家授权，可用于建立店铺主表，并补当前缺失的 `shop_id`、`shop_lat`、`shop_lng`。

- 文档中的 `userId` 指品牌账号，不能填入消费者 `account_id`。
- 文档示例的门店与坐标不是真实采集样本，不能写入业务结果。
- [Store API](https://api-docs.mykeeta.com/apis/standard/shop) 包含商家详情及营业时间等管理能力；营业时间不等于任一时刻的消费者可下单状态。
- [标准 API 资源说明](https://api-docs.mykeeta.com/apis/standard/docs/developresource) 描述开发者账号、应用与测试门店。
- [菜单 API](https://api-docs.mykeeta.com/apis/standard/menu) 的菜单/SKU/规格可帮助构建固定篮子，但商家菜单价不等于指定消费者的券后价。
- 某些官方接口有明确 appId 维度配额，例如图片上传接口；这些配额**不能当作消费者 App 的允许访问频率**。生产准入、巴西适用性、业务用途、接口配额需分别确认。

### 3. 用户条款与访问控制

[巴西用户条款](https://www.mykeeta.com/contents/user.html?locale=pt-BR&region=BR)：

- §4.1.6 明确涉及未经事先书面许可的自动抓取。
- §3.2.2 规定单用户账号及获平台接受的特殊业务集成例外。
- §4.2 涉及暂停或终止访问的措施。

这是当前平台规则的直接证据，不等于已证明本次错误就是按该条款触发。

[巴西隐私政策](https://www.mykeeta.com/contents/privacy.html?locale=pt-BR&region=BR) 列出 IP、设备与使用行为等数据类别。政策允许收集这些信息，**不证明**具体风控算法、当前拦截维度或某种网络配置必然解决问题。

## 建议路线及优先级

### A. 先诊断本次访问异常

保持采集暂停。由用户或官方支持确认普通使用是否恢复，避免自动连续刷新。记录同账号、同设备、同地址、App 版本、发生时间、页面范围和明确错误文案；如果官方诊断能提供 HTTP/业务错误码与请求标识，只保留必要脱敏信息。

一次最小人工验证应回答：正常网络是否可用；Keeta 首页与某一店铺详情是否都报错；错误是否带明确限制原因。没有必要先更换账号或网络。不要将“换网络后一次可用”解释为已建立可持续采集能力。

### B. 优先评估官方授权接入

向 Keeta 技术团队提出以下具体问题（本次仅准备，未发送）：

1. 巴西 15,000 个条件化报价观测/次、每周两次的用途是否可获授权？
2. 是否有下单前的报价/ETA 接口，或可书面允许的消费者页面采样方案？
3. 是否支持指定店铺、配送地址、固定商品篮子、账号类别及已应用优惠？是否无需生成真实订单？
4. 现有商家 API 的授权店铺范围、字段与数据使用许可是什么？是否有适合研究/监测的数据产品？
5. 各接口的请求配额、突发与日配额、错误后的恢复流程和服务支持机制是什么？
6. 是否提供隔离测试店、测试账号和测试 App，用于验证数据模型？沙盒测试结果不能当作真实市场报价。

在这些问题明确前，官方 API 是优先尽调路径，尚不是已完成的解法。

### C. 改进现有实现的请求经济性

以下均为代码复盘得到的工程建议，不能保证消除服务端限制：

- **持久熔断**：进入或离开每个页面时检查访问异常、验证、账号状态；首次 Access error 就中止，不继续进入新店。将暂停状态持久保存，进程重启默认仍暂停，恢复需要明确确认。
- **先记录操作预算**：每次导航、店铺、页面、开始/结束时间、结果和恢复行为写结构化事件。记录成功/失败尝试数与耗时；有授权的网络诊断数据时才计真实业务请求，不拿本地 XML 次数冒充 API 数量。
- **店铺主表**：ID、名称、地址、坐标带来源和更新时间；在允许的更新周期内复用，避免每条报价都进入详情页。可变营业状态及报价仍要独立更新。
- **账号与地址台账**：记录自己的已验证上下文，不用每家店都打开账号页；不以邮箱替代内部 ID，不建立未获准的多账号访问方案。
- **固定店铺队列**：使用已核验店铺标识和正常分享/导航入口，避免反复刷推荐流、进店才发现已采过。只优化导航，不猜测店铺 ID 或私有端点。
- **固定购物篮子**：按店铺记录 SKU、规格、数量和替代规则，降低规格失败与起送价失败。现有 8 条反映实际购物车，不应直接当作跨店统一篮子的比较结果。
- **解析失败离线恢复**：同一报价的证据已在本地时，先修解析并重放，不为 Free、划线价或布局变化重新请求同店。
- **低成本留证**：页面截图与 XML 读取主要是本地成本；减少截图主要节省磁盘/CPU，不能声称它会减少 Keeta 后端请求。

### D. 商业数据商采用实样验收

可并行询价，但先要求：巴西指定城市/店铺的近期真实样例；30 字段逐项来源；P3 而非列表 ETA；账号/地址/篮子/已应用优惠上下文；无需真实下单；数据许可及来源；缺失与失败标记；原始时间证据；去重与稳定交付记录。先验收小批量，再约定规模及 SLA。没有实样的“支持 Keeta”不计为解决方案。

## 30 字段的来源分层

| 数据层 | 示例 | 规模化处理 |
| --- | --- | --- |
| 获授权店铺主数据 | 店铺 ID、名称、地址、经纬度、菜单及规格结构 | 独立同步、版本化缓存；覆盖仅限获授权范围 |
| 自有账号与采集点上下文 | 经核验的账号属性、所选配送地址与坐标 | 用户许可的台账；不能用手机 GPS、品牌 userId 或地理编码猜值替代 |
| 实时条件化报价 | 采集时间、购物篮子、券后价、费用、ETA、距离、当前店铺状态 | 必须由匹配条件的实时来源取得，不能由静态表补造 |

若取得同一目标店铺的有效商家授权，当前 22 项理论上可再补店铺 ID 与两个店铺坐标，达到 25 项；其余账号 ID、会员、采集点坐标与距离仍需独立验证。此处是字段来源潜力，**不是已采 25 项**。

## 规模验收与决策门槛

- 先锁定一条记录的业务定义：店铺 × 账号上下文 × 配送地址 × 固定篮子 × 采集时段。失败不记正常零值或 close。
- 在获准范围内先取得可核验样例，再评估短时和持续运行的成功率、独立有效记录/小时、每条操作/请求量、恢复时间、字段覆盖与成本。
- 15,000 条若要求 12 小时完成，需求为 1,250 条/小时；12 小时只是示例窗口，须按业务确认。今天包含调试的 8 条/约 28 分钟不能用于线性估算设备数量或生产成本。
- 没有实时报价来源、使用许可及稳定性证据时，尚不能承诺每周 30,000 条。数据接入问题应作为项目可行性里程碑，而非“解析细节优化”。
